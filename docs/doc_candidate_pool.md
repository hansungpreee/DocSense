# 대분류별 후보 풀과 편입 기준 · 새 개발용 OOD 설계 (8주차 1~2일차, 백엔드 2)

> 작성 2026-10-26. **이 문서의 후보는 모두 제안이며 10/29 회의에서 정합니다.** 후보 풀의 문서는 **편입되기 전에는 소분류가 아닙니다.** 「기타」 정답으로 쓰는 개발용·최종 OOD 문서도 마찬가지로 소분류가 아닙니다.
> 비즈폼 등에서 **양식을 구할 수 있는지는 아직 확인하지 않았습니다**(표의 「양식」 칸 미확인). 편입 기준 ②가 충족돼야 풀에서 소분류로 올립니다.

## 1. 편입 기준 (회의 결과 2절)

한 문서를 풀에서 소분류로 올리려면 아래 세 가지를 본다.

1. **닮아서 분리가 필요한가.** 기존 소분류와 겉모습·항목이 닮아 「기타」로 안 가고 새는(개발용 OOD에서 실제로 샌) 문서가 우선. 닮은 소분류가 없는 문서는 급하지 않다.
2. **양식을 구할 수 있는가.** 실제 공개 양식(비즈폼 등)이 있어야 하고, 기존 양식과 **내용·항목·레이아웃이 다른** 새 양식을 만들 수 있어야 한다(숫자만 바꾼 복제 금지). 양식 1종 ≈ 10건(fewshot 1·dev 4·test 5).
3. **대분류 균형.** 한 대분류에 몰리지 않게 하고, 소분류가 1개뿐인 경영/전략을 보강한다.

그 밖에 지킬 점:
- 최종 OOD 3종(법인카드지출결의서·주간업무회의록·부서간업무협조전)은 **풀에 넣지 않는다.** 소분류가 되면 최종 평가의 OOD가 사라진다.
- 편입한 종류는 개발용 OOD 쪽에서 빠진다(「기타」가 정답이 아니게 되므로). 그래서 승격 6종이 끝나면 개발용 OOD 6종이 모두 사라진다 → 3절에서 새로 설계한다.
- 프롬프트 「기타」 정의에는 예시를 넣지 않는다(`taxonomy_definition_check.md` 추가 수정 4). 풀 목록이 프롬프트에 들어가서는 안 된다.

## 3. 새 개발용 OOD 종류 설계 (2일차, 가안)

### 왜 필요한가
- 승격 6종이 소분류가 되면 현재 개발용 OOD 6종이 모두 「기타」 시험 재료로 못 쓰인다. 확신도 기준(0.7 → 0.95?)을 정하고 `NEW-xx` 흐름을 확인하려면 **개발 단계 내내 쓸 OOD가 따로 있어야** 한다.
- 최종 OOD 3종을 보고 기준을 정하면 최종 평가가 오염된다 → 겹치지 않는 종류로 만든다(`render_ood.py` 머리말의 같은 원칙).

### 설계 원칙
1. 사내 미등록 문서와 사외 문서를 섞는다 (회의 결정: 사내 미등록 3 + 사외 3 제안).
2. **최종 OOD 3종·현재 개발용 6종·풀 편입 후보와 겹치지 않는다.** 풀 후보를 OOD로 쓰면 편입 때 다시 바뀐다.
3. 「기타」 정의 예전 예시(지출결의서·활동보고서·출장정산서)와 같은 낱말을 문서에 쓰지 않는다. 문서 안에 「OOD」·「분류 체계 외」 같은 단서를 넣지 않는다.
4. 닮은 소분류가 있는 종류(새는지 보려는 것)와 없는 종류를 섞는다.
5. 종류당 10건, 시드·폴더·라벨·코드를 기존 `ood_dev`와 **따로** 둔다(`DEVOOD-07~`).
